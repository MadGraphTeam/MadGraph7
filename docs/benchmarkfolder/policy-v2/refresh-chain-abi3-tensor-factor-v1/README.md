# Held refresh chain for the QP tensor-factor commit

This prospective package launches nothing during preparation. Root owns source validation, staging, commit, resource allocation and phase launch. All frozen policy/collector tools, physical inputs and legacy bindings are reused exactly. No existing evidence is modified.

Execution dependencies:

1. Commit the numerical source and pass development NLO validation; keep generator sources fixed throughout fresh CLI exports.
2. Run `generation-abi3-tensor-factor-v1/commands.sh` for all 13 clean exports and the live runtime inventory. New standalone/internal-copy/FKS export validation remains root-owned.
3. Run `final-candidate-plan-abi3-tensor-factor-v1/commands.sh`: eight candidate targets, full 10-point fresh parity/two commands, then combine only these NEW candidate bindings with the12 unchanged eligible legacy bindings into a NEW proof.
4. Run `final-controls-plan-abi3-tensor-factor-v1/commands.sh`:11 new candidate targets, reusing five new representative targets and all 12 old corrected-original control targets; compare all 21 pairs per case/two commands.
5. Prepare/run/compare `final-variant-controls-abi3-tensor-factor-v1` in coordinated stages, preserving old failed and successful attempts.
6. After the unchanged full 8 corrected-original24h reference qualifies and root grants quietCPU207, run `final-core-plan-abi3-tensor-factor-v1-24h/commands.sh`. Publication is separate and all 8 correctness/performance gates remain mandatory.

Existing correction postimages are reused only after new generated model manifests match exactly. The installed ABI3 numerical archive/module/link metadata must remain identical; otherwise refresh the affected exact runtime groups and ABI-level controls too. Collection runs retain their own namespace and refuse overwriting earlier results. New render/profile artifacts must refer to the eventual new dataset and actual new generation evidence.

Use `python -B docs/benchmarkfolder/policy-v2/refresh-chain-abi3-tensor-factor-v1/verify.py` for static preparation verification only. It parses scripts/specs, checks exact permitted source/spec deltas and unchanged reuse identities, and performs no build or amplitude evaluation.

Resource plan: generation/build descendants inherit CPUs7,8 by default; candidate representatives, generated controls and variants use CPU5 and run Symbolica sequentially; final acceptance remains CPU207 after the existing reference collector finishes. No phase is launched by preparation.

`static-check-resource-update.log` is the final unlaunched preparation check with the agreed CPU assignments. Earlier static-check logs retain the preparation sequence. `reuse-check-tests.log` records four read-only checks: the existing thirteen-case postimages/runtime pass, while altered model bytes, runtime signature, or module/link metadata reject reuse. `independent-static-review.log` records a separate successful review/verifier run; no phase was launched.
