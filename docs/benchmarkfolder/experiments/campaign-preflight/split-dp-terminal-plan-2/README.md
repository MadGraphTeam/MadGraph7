# Proposed campaign with the three qualified terminal rank pairs

This second planning snapshot supersedes the proposed scope of plan1 without
altering its historical files. It is **not a registered campaign**. The final
production commit remains pending until the coordinator accepts deterministic
control/candidate generation, whole-amplitude qualification and the protocol
audit. No numerical jobs, baseline relinks or campaign registration are started
by this inventory.

The proposed ID is `split-dp-terminal-rank3-1`, with predecessor `legacy`. The
intended implementation combines the already installed split DP workspaces with
guarded terminal rank pairs `(1,1)`, `(2,1)` and `(3,1)`. The latter two extend
the production basis `8ae62e25d85b1c6c81f37ccdb86f71bc550ed16a`. This planning
snapshot records the actual observed source bytes, including a dirty flag and
patch hash if the extension is not yet committed. Those observations are not a
substitute for the final clean source identity sealed at registration.

The package remains the actual CLI-installed
`.tirust-build/current-install/mg/HEPTools/tirust` with DSO SHA256
`095e957990c2e7ed87ed9ea73fee71eb132f00b330e0d38fd423163c173e358c`.

## Deterministic generation and preserved baseline

New child MG CLI processes must use `PYTHONHASHSEED=0`, overriding the inherited
environment. The new manifest and fresh generation records bind this value and
its version; missing or changed live bindings fail closed. This fixes ordering
of otherwise independent generated blocks and targets across fresh exports.
The source and compiler checks still compare actual generated files and flags.
Seed metadata alone cannot open another numerical identity or erase a failed
performance gate.

The eleven baseline exports retain their exact frozen generated sources,
source-built numerical objects, compiler flags, native dependencies and
executable identity. Their historical export seed was unrecorded and remains
unrecorded. The deterministic relink environment is recorded separately; reuse
does not regenerate or reorder their Fortran. Before copying each baseline,
require its untouched driver and current source-bound objects to reproduce the
recorded executable byte for byte. Failure requires a full source build.

Each candidate is generated afresh through the actual CLI with the fixed seed
and `--no_save` configuration commands, then built from generated sources. There
are eleven candidate exports; no old candidate numerical objects are reused.
The coordinator's deterministic pair qualification must demonstrate that
unchanged generated files remain identical after normalizing only documented
identity/path differences, leaving the intended polynomial/call changes
explicit. Final acceptance still checks the complete physical amplitudes.

## Proposed registration and ordered execution

After final source and protocol approval, the registration command is:

```sh
source tools/tirust_env.sh
python3 tools/tirust_benchmark.py register-campaign \
  --campaign split-dp-terminal-rank3-1 --predecessor legacy \
  --tirust-prefix "$PWD/.tirust-build/current-install/mg/HEPTools/tirust" \
  --reason 'Split primary/check DP workspaces and guarded terminal rank pairs 1x1, 2x1 and 3x1' \
  --worker-timeout qcd_n4_uux_zzgg=14400 \
  --worker-timeout ew_n4_epem_mupmumaa=14400
```

All other cases use 3,600 seconds. These are per-startup/protocol administrative
limits; they do not shorten the point streams, timed batches or repetitions.
The actual final source/native/environment/timeout identity is frozen by the
manifest, not this proposal.

Then reuse and privately relink all baselines, perform all eleven fresh CLI
candidate source builds and complete baseline CutTools plus all five explicit
candidate backends on every saved 100-point stream. Untimed `--warmup-only`
preparation may use the final complete steady traversal; an incomplete stream
never qualifies. Numerical validation is a separate prerequisite to timing.

Keep the unchanged shared policy: `MLStabThres=1e-6`, Init1/Run−1, forced host
stability checks, full finite and UV/IR coefficients, frozen physical cards,
QP-integrand and cache settings, and both frozen UFO models. Materialized
baseline main/mixed chains are `8|6|7|1`; loop-induced controls use `7|6|1`.
Candidate chains prepend 9. Preserve all earlier failures and adjudications.

After all owned compilation and diagnostic jobs finish and the host recovers,
sample allowed CPU/sibling load and freeze the selected CPU. Complete all eight
main chain gates first: seven alternating pairs, all 100 points on every
traversal, sustained calibration toward two-second batches and upper 95% ratio
bound ≤1.05 per process. Any failed/ineligible main gate remains authoritative
and defers the expensive later phase. If all pass, finish explicit-backend
regressions and controls. Main existing backends 1/6/7/8 retain their speed
gates; standalone9 and control speed comparisons remain descriptive.

The historical scheduling model remains incomplete: approximately 17 hours of
known main work plus unknown heavy lanes and candidate-chain costs, compilation,
numerical preparation and external queues. Several n4 explicit9 streams never
completed under their old administrative bounds. Plan for hours of preparation
and potentially multiple days of full successful timing; do not infer a finite
schedule bound or performance success from private kernel measurements.

`readiness.json` binds the current read-only inventory and the fixed export
environment. It may show a pending dirty extension; root must freeze a clean
approved revision before the registration above. Plan1 remains unchanged.
