# Source audit: repeated Born/color contractions

Identical color rows offer a bounded, exact reuse opportunity inside
`CREATE_LOOP_COEFS`. Cache the **unscaled** Born contraction for a row and
amplitude-order index, separately in DP and QP, for one helicity's coefficient
construction only. Keep every original diagram's multiplier, symmetry factor,
helicity weight, output order, and loop-group destination.

The inventory below comes from source/data inspection. Later isolated
prototype tests are described at the end. No production source was edited.

## Current calculation and exactness boundary

`madgraph/iolibs/template_files/loop_optimized/polynomial.inc:70` clears
`CONST(NAMPSO)`. Lines 76–80 visit Born amplitudes in ascending index order,
convert the integer color coefficient in the selected precision, apply the
imaginary phase encoded by a negative denominator, and accumulate
`CFTOT * CONJG(AMP(I))` into the Born amplitude's split-order bin.

That entire loop is identical for identical integer rows during one immutable
`AMP` epoch. A cache miss must execute the existing loop unchanged, including
its order and precision. A hit copies the previously computed unscaled
`CONST` vector. Lines 82–90 must still apply the current `MULTIPLIER/SYMFACT`,
conditional `GOODHEL(HELCONFIG)`, and original `COLOR_ID`'s loop split order
before `MERGE_WL`. Never scale the cached vector in place.

Two color-identical diagrams need not have the same loop split order,
symmetry factor, multiplier, or loop group. Those quantities are not part of
the reusable Born contraction. The mixed-order control is therefore essential
to testing the separation.

The neighboring counterterm loops have a different arithmetic structure:
`(CFTOT * AMPL) * CTEMP` for each Born amplitude. Replacing them with the
cached summed contraction would reassociate products and sums. They should
remain unchanged in an exact-reuse prototype.

## Where state becomes valid and where it must expire

The integer matrices are generated by `get_color_matrix`
(`madgraph/loop/loop_exporters.py:705`) from exact rational color data and written
to the two `Color*Factors.dat` resources at lines 1717–1726. They are loaded
under `LOCAL_ML_INIT` in
`madgraph/iolibs/template_files/loop_optimized/loop_matrix_standalone.inc:598`
and `:607`. Build the row-class map from the **loaded** arrays, after both
reads. This preserves runtime resource replacement and avoids trusting an
export-time equivalence map if a user changes the resource files.

The safest bounded cache epoch is each entry into the coefficient-construction
batch, after all Born HELAS calls for its current helicity:

- DP: reset valid-row flags immediately before `%(coef_construction)s` in
  `loop_matrix_standalone.inc:1117`, inside the H loop beginning at line 1041.
- QP: reset the QP flags before `%(mp_coef_construction)s` at
  `mp_compute_loop_coefs.inc:457`.
- QP rescue with a DP integrand: reset the **DP** flags before
  `%(coef_construction)s` at `mp_compute_loop_coefs.inc:461`. Merely resetting
  QP flags on entry to the rescue routine is insufficient.

Reset once before the first generated chunk, not at each
`COEF_CONSTRUCTION_n` call. Multiple chunks and loop diagrams share `AMP`.
The generated chunk only reads its Born `AMP` common block while constructing
loop wavefunctions.

This epoch naturally expires across new phase-space points, helicities,
helicity-filter initialization/retries, rotated stability checks, changed
couplings/scales/masses, and QP reconstruction. The MP code explicitly clears
the amplitude arrays, rebuilds them in its selected lane, and sometimes
promotes DP amplitudes into QP containers
(`mp_compute_loop_coefs.inc:290`, `:394`). A persistent cache keyed solely by
helicity would be wrong.

`CHECKPHASE`, `HELDOUBLECHECKED`, `HELPICKED`, and `GOODHEL` affect the later
helicity weight, which remains outside the cached value. Split-order selection
controls which chunks/diagrams execute, so use a **lazy** row cache: eagerly
contracting all classes would perform arithmetic that the original filtered
path might never execute.

The row map is integer metadata shared by both precision lanes. The cached
complex vectors and validity flags must be separate per lane. A conservative
fixed-size allocation using `NCOLORROWS * NAMPSO` needs about 48 KB total
DP+QP for QCD3, 248 KB for QCD4, and 681 KB for EW4; sizing by actual row
classes could reduce that further. No cross-phase-point entries are needed.

## Split-order lookup and floating-point considerations

The generated `ML5SOINDEX_FOR_BORN_AMP` and
`ML5SOINDEX_FOR_LOOP_AMP` functions return constant `DATA` maps.
`ML5SQSOINDEX` sums order vectors and searches their squared-order map.
For QCD3, see `loop_matrix.f:2168`, `:2198`, and `:2328`.
The source has getters and a target selector; it has no normal runtime setter
that changes the order-definition tables. These integer maps can be generated
or initialized once, but they are a separate improvement from row caching.
Keep original lookup calls on the cache-miss path for the first prototype.

Do not preconvert rational color factors once for the entire process without
handling rounding-mode changes. Computing the original conversion lazily
inside the per-helicity epoch retains the current precision and rounding mode.
If exact exceptional behavior matters, disable contraction reuse when the
current Born amplitudes are nonfinite; this preserves repeated original
arithmetic and avoids assumptions about NaN payload/exception behavior.
The existing generated pipeline does not change the rounding mode between
diagrams in a batch.

For an implementation that must preserve direct low-level calls outside the
normal driver, enable caching only between explicit begin/end batch calls;
otherwise `CREATE_LOOP_COEFS` can retain its original path. Standard MadLoop
already uses per-process common blocks and is not made more thread-safe by
this proposal.

## Existing cost evidence and next checks

The retained original-Fortran `gprof` samples assign CREATE itself 1.02% for
QCD2 and 1.59% for QCD3; split-order helper self samples add roughly 1–1.5%,
but those helpers also serve counterterm code. `MERGE_WL` is a separate
1.53%/2.42% and is not removed by contraction caching. Those profiles exclude
dynamic reducer self samples and include initialization, so these are not
fractions of whole-process wall time or projected speedups. The retained EW2
`perf` sample assigns CREATE 1.47% and MERGE 0.99%.

There is no isolated QP CREATE timing yet. Very high row reuse in EW3/EW4
justifies a bounded prototype after the higher-priority compact-QP sparsity
study, but does not establish a performance gain.

Required checks before promotion: unchanged complete point/order coefficients,
accuracies and statuses; mixed-order target selection; DP, QP and DP-integrand
rescue; initialization and helicity changes; point/scale/mass rebinding;
resource-row changes at fresh initialization; inactive cache path for
loop-induced output; and alternating measured repetitions against the same
unmodified generated output. No production change is proposed without those
results.

## Isolated prototype and measured limitation

`prototype.py` implements the bounded cache only in copied generated files.
It maps the actual loaded integer rows at initialization, resets precision
specific validity flags at each coefficient-construction batch, and disables
the cache after that batch. It preserves the original miss contraction,
including every Born-index lookup and the accumulation order.

`check_exact.py` compiles the actual mixed-order CREATE and MERGE routines.
All 1,280 DP and 1,280 QP tests pass complete LOOPCOEFS bit comparisons and
cumulative batch IEEE flags. The tests vary amplitudes between epochs, mutate
color resources with map invalidation, exercise imaginary color factors,
multiple split orders, distinct loop-group destinations, symmetry factors,
multipliers, helicity weights, NaNs, signed zeros, and direct calls with the
cache disabled.

There is an explicit internal-batch constraint: user code must not clear IEEE
flags between cached calls. A cached contraction does not re-raise
IEEE_INEXACT when its arithmetic is omitted. The ordinary coefficient batch
does not clear those flags, so cumulative flags agree. The adversarial
per-call-clear failure is preserved in `per-call-flag-boundary.json` and its
test in `check_per_call_flags.py`; it must not be presented as an unrestricted
replacement for arbitrary low-level calls. Direct calls outside the bounded
batch retain the original computation.

The first five paired EW 2→2 process trials reproduce all coefficients,
accuracy estimates and return codes, but the cached median is **1.07737 times
the original**. With two Born amplitudes, the overhead exceeds the saved
contractions. Evidence and exact source snapshots are in `ew2-five-pair/`.
The first three-pair EW 2→3 trial, with eight Born amplitudes, was also slower:
ratio 1.05325. Disassembly identified an avoidable cost: exposing
IEEE_ARITHMETIC through the cache module caused the compiler to insert IEEE
entry/exit handling into every CREATE routine.

Version 2 moves that import into the batch-begin helper only. All 2,560 compiled
exact tests still pass. The subsequent five-pair EW2 ratio is 0.998889, with
substantial run-to-run noise; the three-pair EW3 ratio is 0.972460. Every
coefficient, accuracy estimate, row status and timed rescue count remains
exact. The evidence is in `ew2-v2-five-pair/` and `ew3-v2-three-pair/`.
These results do not establish an acceptance speedup. The small possible
gain, extra state, and IEEE-flag constraint mean this remains an unpromoted
experiment.

The process runner shares the isolated full-evaluation runner in the sibling
`expanded-wl-sparsity` experiment. It uses Ninja6, keeps 100 identical points,
alternates the variant order, and checks every printed coefficient, accuracy,
row status and timed rescue count. These concurrent-host trials remain
exploratory, with no production or accepted-benchmark data changes.
