Command-Line Interface¶

The pyamplicol command covers the complete user workflow: inspect or compile a model, plan or generate process artifacts, inspect their physics axes, evaluate phase-space points, and profile the optimized runtime. The same schema also drives the typed Python API.

[!TIP] Start with the four-card walkthrough in Quick Start. This page is a command map, not a requirement to configure every available switch.

Command map¶

pyamplicol generate "d d~ > z g" artifacts/builtin_ddbar_to_zg --model built-in-sm

pyamplicol evaluate artifacts/builtin_ddbar_to_zg --momenta point.json

Cards, direct options, and overrides¶

There are three equivalent ways to supply configuration:

  1. a schema-v1 TOML card;

  2. dedicated command-line options;

  3. repeated --set PATH=VALUE overrides.

Configuration precedence is:

defaults < TOML card < dedicated CLI options < repeated --set overrides

Any license or resource clamp is applied last and reported in the effective configuration. Unknown fields are errors rather than silently ignored.

Run a card directly:

pyamplicol generate_pp_zjj_from_ufo_sm.toml

Use an explicit action when the same card supplies shared settings:

pyamplicol generate --card qq_z6g_recurrence_jit_o2.toml
pyamplicol profile --card qq_z6g_recurrence_jit_o2.toml

One card, the action on the command line¶

pyamplicol CARD ACTION [options] runs ACTION (generate, check, evaluate, profile, inspect) with CARD as its card: one card can carry the settings of every action, and the card’s own action is what pyamplicol CARD alone runs. --output DIR names the artifact, relative to the working directory: the directory generate writes (generation.output) and the one check, evaluate, profile and inspect read (evaluation.artifact). Every other option is the action’s own, for example --process (one or more process expressions, MG5_aMC syntax accepted, replacing the card’s entries) and --set PATH=VALUE. The shipped master card loop_generate.toml is made for this (One-loop examples):

pyamplicol loop_generate.toml generate --process="u u~ > d d~ QCD^2<=4 QED^2<=6 [QCD QED]" --output=./my_loop_output
pyamplicol loop_generate.toml check    --output=./my_loop_output
pyamplicol loop_generate.toml evaluate --output=./my_loop_output
pyamplicol loop_generate.toml profile  --output=./my_loop_output

It is the same as pyamplicol ACTION --card CARD --set generation.output=DIR (or evaluation.artifact=DIR); the forms pyamplicol CARD, pyamplicol check CARD and pyamplicol ACTION --card CARD are unchanged.

MG5_aMC process syntax¶

A process expression (--process, a card’s process.entries, or a string given to pyamplicol.generate / Generator.plan / Generator.generate) may be written as on an MG5_aMC generate line. The annotations are translated into the run-card settings that express them, in one place for all three entry points; the generation log names the translation (INFO pyamplicol.cli: process 'u u~ > d d~ [QCD]' (MG5_aMC syntax) -> 'u u~ > d d~' with process.loop_coupling_orders = ["QCD"]), config resolve shows it in the effective configuration, and the requested configuration keeps the expression as written.

MG5_aMC

pyAmpliCol setting

[QCD], [virt=QCD], [all=QCD], [QCD QED]

process.loop_coupling_orders (only the one-loop virtual is computed: [QCD] means the virtual)

[noborn=QCD], [sqrvirt=QCD]

process.loop_coupling_orders and process.loop_induced = "only" (loop-induced |A_loop|^2; processes with a Born are not served this way)

QED=2, QED<=2

process.max_coupling_orders (Born amplitude orders)

QCD^2<=4, QED^2==6, QED^2>2 (also <, >=)

process.squared_coupling_orders (sector selection)

/ z h

generation.particle_veto

An amplitude- or squared-order constraint also sets process.coupling_order_policy = "explicit", as MG5_aMC drops its WEIGHTED minimisation when coupling orders are named: every Born amplitude order within the limits is generated. The NLO bracket comes last; a trailing bracket is MG5_aMC’s when it holds = or names coupling orders in MG5_aMC’s upper-case spelling, otherwise it is an anonymous multiparticle (u u~ > d [d g]). Refused with the typed madloop-syntax error: [real=QCD] and [LOonly=QCD] (only the virtual is served), decay chains (t t~, t > b w+: request each decay as its own process), $ / $$ s-channel exclusions, @N tags and amplitude-level == / >. A translated setting that the card, an option or --set also states with another value is a typed error naming both (ProcessSyntaxConflict); several process entries must carry the same annotations, since the settings are run-wide. A plain ProcessRequest takes plain expressions and refuses MG5_aMC syntax with the translation it would have.

Override one leaf without editing the card:

pyamplicol generate_pp_zjj_from_ufo_sm.toml \
  --set generation.workers=2 \
  --set generation.mode=replace

--set is deliberately repeatable and order-sensitive. For commonly used fields, prefer the readable dedicated form—for example --workers 2, --execution-mode eager, or --color-accuracy nlc.

For the complete field reference, see Configuration or create an annotated local template:

pyamplicol config template pyamplicol.toml

Generate¶

The shortest built-in-model command is:

pyamplicol generate "d d~ > z g" artifacts/builtin_ddbar_to_zg \
  --model built-in-sm

Useful generation options include:

  • --process EXPRESSION to add another request;

  • --name NAME to name a request;

  • --multiparticle 'p=d,d~,g' to define a multiparticle label;

  • --flavor-scheme N and --max-quark-lines N to constrain expansion;

  • --flavor-blind to generate one subprocess per flavour-relabelling class, or --flavor-blind-strict to route only the relations that are symmetries of the allowed vertices (see Group equivalent subprocesses);

  • --analyze-process-groups {none,numerical}, --only-unit-multiplier, and --[no-]consider-charge-conjugation to search the generated subprocesses for equal matrix elements;

  • --color-accuracy {lc,nlc,full};

  • --color-contraction {direct,symmetric-group-fft};

  • --fft {trace,adjoint} as a shorthand selecting symmetric-group FFT and its basis;

  • --correlators FILE.json to prepare named colour operators and allowed spin replacements for the Python and native correlated APIs;

  • --lc-flow-layout {topology-replay,all-flow-union};

  • --execution-mode {recurrence,compiled,eager,on-the-fly};

  • --backend {jit,asm,cpp};

  • --workers auto|N;

  • --mode {error,append,replace} or the --force shortcut for replacement;

  • --no-emit-api-bundle when standalone drivers are not wanted;

  • --numerical-current-reuse to search for certified numerical current relations at generation time (off by default because the high-precision probes are costly);

  • --post-build-validation for an optional immediate native total-versus- resolved smoke after writing the artifact;

  • --loop-induced-probes to run the generation-time finiteness, Ward and Goldstone probes of loop-induced processes (binary64, double-double where a binary64 probe fails or is refused; off by default because the written artifact does not depend on them; they validate a new or edited loop UFO, see Configuration), and --allow-failed-probes to store a process whose probe failed (it acts only with the probes on).

The summary table after a generation lists the output, the processes, the existing-output policy, the schema version, the files, and two measurements of the generation:

  • generation time: the wall-clock time of the whole generate call, from reading the processes to the last validation (the start-up of the command before it is not included), in bold, then, in brackets, each generation phase (setup: reading the request and loading the generation engine; then the phases of the progress display) and the unattributed rest, which add up to it;

  • peak RAM: the most memory the generation needed at once, the peak resident memory of the generating process (its threads, native thread pools included) and of every process it started (compilers of the cpp backend).

On Linux the process’s peak is the kernel’s high-water mark VmHWM, reset at the start of the generation (/proc/self/clear_refs): exact. The reset is process-wide, so pyAmpliCol does it only in a process it owns (the pyamplicol command and its worker processes): called as a library (Generator.generate, BenchmarkRunner, from MadGraph7 or a script), it never lowers the calling program’s own peak (VmHWM, ru_maxrss, what time -v reports) and reads the lifetime peak instead, as below. Where the reset is refused, and on macOS (getrusage ru_maxrss), only the process’s lifetime peak is known: it is the generation’s when the generation raised it, else an upper bound, shown <= x. Started processes are followed by a thread that sums the resident sizes of the process tree every second (Linux: the /proc children lists; macOS: ps) and, on Linux, by the largest peak of an ended one (getrusage RUSAGE_CHILDREN); with started processes the peak is shown >= x (processes running together may have needed more), followed by the generating process’s own peak when the peak is not it and, when above it, the largest one of a started process (the kernel credits a started process with the resident size of the process that starts it, so a smaller one says nothing). The default jit backend and the one-loop engine start no process, so their peak is exact on Linux. --fields-description-help describes each row, and --json carries the same values under statistics: wall_seconds, phases (a list of {"phase", "seconds"}), unattributed_seconds, peak_rss_bytes, peak_rss_bound (exact, upper bound, lower bound, approximate or unknown), peak_rss_method, process_peak_rss_bytes, child_processes and child_peak_rss_bytes. The artifact stores them too (see Artifacts and Portability), so inspect shows them later.

Planning is non-writing:

pyamplicol generate "p p > Z j j" artifacts/unused \
  --model models/json/sm/sm.json \
  --multiparticle 'p=d,d~,g' --multiparticle 'j=d,d~,g' \
  --flavor-scheme 2 --max-quark-lines 2 \
  --execution-mode compiled --dry-run

Adaptive --fft adjoint is the recommended starting point for exact FFT colour contraction. It selects certified DDM where valid and otherwise retains exact fundamental-chain or trace tensors. Select contracted colour and a supported execution lane (recurrence or on-the-fly) explicitly:

pyamplicol generate "g g > g g g" artifacts/ggg_adjoint_fft \
  --model built-in-sm --color-accuracy full \
  --fft adjoint --execution-mode recurrence

Use --execution-mode on-the-fly for the compact OTF counterpart. The same option works for quark processes, using their existing fundamental chains:

pyamplicol generate "d d~ > z g g" artifacts/quark_zgg_fft \
  --model built-in-sm --color-accuracy full \
  --fft adjoint --execution-mode recurrence

For a certified n-gluon tree, DDM fixes two gluon anchors and retains (n-2)! orderings instead of (n-1)!. Certified single-insertion HEFT also uses DDM: see examples/builtin_sm_heft.toml, which explicitly sets HIG = 1. Other interactions retain their exact trace representation; multi-quark-line processes retain fundamental-chain products, not a JO primitive basis. The saved fft_basis_selection states the requested and actual basis and the selection reason. --fft trace forces the original representation. Both requests preserve full or nlc accuracy; forced adjoint FFT rejects correlations. In the benchmarked pure-gluon family the adjoint basis was faster than trace for six or more external gluons (3.9x per sample and 4x faster generation at ten gluons); at lower multiplicity the two are comparable, so compare warmed evaluation and setup costs for other workloads. --color-contraction symmetric-group-fft remains valid and defaults to adjoint. Without an explicit contraction flag, NLC/full recurrence and on-the-fly generation automatically try adaptive adjoint FFT and fall back to direct if the FFT plan is unsupported. LC, compiled/eager, and correlated generation remain direct/trace. Use --color-contraction direct to opt out. Do not combine --fft and --color-contraction; use either spelling. Card settings are overridden by dedicated flags, then by ordered --set options as usual.

--dry-run performs the operation exposed as Generator.plan(). It creates no artifact, output directory, or compiled-model cache entry. A raw UFO or JSON source must already have a reusable compiled-model cache entry, or be compiled explicitly, because planning never compiles trusted model input as a side effect. A one-loop dry run runs the request-model preparations and so fills the one-loop preparation cache (unless it is off), preparing a later generation ahead.

See Generation Modes and Evaluators before combining execution modes and prepared-model backends.

Correlated Born quantities¶

The Born Correlations guide gives the declaration format and complete runtime examples:

pyamplicol generate 'g g > g g' artifacts/gg_correlated \
  --model built-in-sm --color-accuracy full --correlators correlators.json

--correlators is a generation option, separate from the ordinary TOML colour settings. --color-accuracy lc|nlc|full selects the correlated approximation (the ordinary default is LC). Complete amplitudes are generated in all cases; direct contraction and generic compiled execution are selected, with those adjustments recorded in the effective configuration. Partial helicity/colour generation, append, and --dry-run are not supported on this path. Numerical spin-vector setting and correlated evaluation use Runtime.set_spin_correlation_vectors(...) and Runtime.evaluate_correlated(...) or Runtime.evaluate_correlated_many(...) in Python, or the corresponding native SDK calls, not the CLI evaluate command.

Inspect and select a process¶

List an artifact’s stable process IDs and coverage:

pyamplicol inspect artifacts/pp_zjj

Focus on one public process ordering:

pyamplicol inspect artifacts/pp_zjj --process 'd d~ > g z g'

The selector may be a stable process ID, an explicit alias ID, an exact stored expression, or a unique side-preserving permutation of one. See Process Selection and Permutations for the ordering contract.

Inspection does not execute evaluator state. Human output uses compact colored tables; machine output is available with --json.

The Artifact table shows, after created, the generation time and the peak RAM of the generation that wrote the artifact, as the generate summary showed them; an artifact written before pyAmpliCol recorded them shows a muted -. --json carries them as generation_statistics (null when not recorded).

The Process groups section shows the artifact’s process-group map: an overview row, then one table of groups, each representative in bold followed by its members. Colours mark generated (green) and routed (cyan) members, C (magenta), factors other than 1 and warnings (yellow), and the basis of each relation. When every process is its own group, the section is the single line Process groups: none; each of the N processes is its own group. Group equivalent subprocesses¶

Every artifact records in process-groups.json which subprocesses share one matrix element, up to a rational factor and a leg permutation. By default each generated subprocess is its own group.

generate --flavor-blind assumes that subprocesses related by a relabelling of flavours with equal spin, colour, mass, and width (and, unless --no-consider-charge-conjugation, by charge conjugation) are equal. Only one representative per class is generated; the others are recorded as its members and exported to UMAMI through the representative’s runtime. The assumption is not verified: a warning names the members whose relabelling is not a symmetry of the model couplings, for example electroweak couplings of different quark flavours.

Generation logs the outcome of this pre-grouping before any representative is generated:

INFO pyamplicol.generation: Flavor-blind grouping: 486 subprocesses -> 23 generated representatives; 463 routed members (140 by charge conjugation); 0 relabelling warnings

The summary table printed at the end has a process grouping row, coloured like the inspect display, read from the written process-groups.json (abridged):

| processes              | 23 requests                                                                              |
| process grouping       | 486 subprocesses -> 23 groups: 23 generated, 463 routed                                  |
|                        | 463 flavor-blind relations (140 charge-conjugated); 0 warnings                           |
|                        | numerical analysis: 3 points, tolerance 1e-09                                            |

Its first line counts the subprocesses, groups, and generated and routed subprocesses; the second, the relations by basis, those that are charge-conjugated or have a factor other than 1, and the relabelling warnings; the last ones, each recorded numerical analysis. The Generated Processes table gains a group column: the size of each representative’s group, or member of REPRESENTATIVE for a member generated in its own right, followed by its factor when it is not 1 and C when the relation is conjugated, as in member of d_dbar_to_a_a (x16). When every subprocess is its own group, the column is omitted, and so is the row unless an analysis was recorded; the row then reads no relation found; each of the N processes is its own group.

The numerical analysis compares generated subprocesses with equal external particle types at three random phase-space points and merges those whose resolved components agree up to one common rational factor:

pyamplicol generate "p p > j j" artifacts/pp_jj --analyze-process-groups numerical
pyamplicol group-processes artifacts/pp_jj --only-unit-multiplier

group-processes runs the numerical analysis (its default) on an existing artifact and rewrites process-groups.json in place; the artifact ID and the UMAMI export are unchanged. --only-unit-multiplier accepts only relations with factor 1. Subprocesses generated with a selected helicity or colour subset are never grouped numerically. Process Grouping describes the relations, the warnings and the file format in full.

Evaluate¶

Evaluate a momenta file with optional parameter updates:

pyamplicol evaluate artifacts/pp_zjj \
  --process 'd d~ > g z g' \
  --model-parameters data/model_parameters.json \
  --momenta data/pp_zjj_momenta.json

Request all physical components rather than only the optimized sum:

pyamplicol evaluate artifacts/pp_zjj \
  --process 'd d~ > g z g' \
  --momenta data/pp_zjj_momenta.json \
  --resolved

Split recurrence totals by squared coupling order with --orders; the JSON output carries values [point][order], the unchanged total, the squared orders with their contributing amplitude-order pairs, and amplitude_orders:

pyamplicol evaluate artifacts/pp_zjj \
  --process 'd d~ > g z g' \
  --momenta data/pp_zjj_momenta.json \
  --orders

Global selectors may be repeated:

pyamplicol evaluate artifacts/pp_zjj \
  --process p_p_to_z_j_j_3 \
  --helicity 'h:-1,+1,-1,+1,+1' \
  --color-flow 1 \
  --momenta data/pp_zjj_momenta.json

--color-flow accepts either a stable flow ID or the one-based ordinal shown by inspect. Flow selection is LC-only; NLC and full-color artifacts expose a contracted color output and accept helicity selection only. More examples are in Runtime and Selectors.

Evaluate without a momenta file¶

Without --momenta (evaluation.momenta), evaluate and profile draw flat phase-space points set by [evaluation.phase_space] (the product’s flat generator, RAMBO on diet, S. Plätzer, arXiv:1308.2922: uniform in Lorentz-invariant phase space, beams along +-z; massive final states through the paper’s mass mapping, whose weight is not applied to the drawn points; a continuous distribution, so no planar or otherwise special configuration is drawn; reproducible bit for bit in the seed; 1.0.3 and earlier drew classic RAMBO points, so the same seed now gives other points): points points (default 2), point i from seed seed + i (default seed 1), at the centre-of-mass energy sqrt_s of a 2 -> n scattering (default: the energy of the artifact’s own validation point, so any process the artifact holds is above threshold). A 1 -> n decay is drawn in the rest frame of the decaying particle, a 2 -> 1 process at its single point (its energy is fixed by the masses). The external masses are those of the artifact’s validation point (massless and massive legs alike; nothing is read from the model). A virtual evaluation then takes mu_r^2 = s per point unless evaluation.mu_r2 is set:

pyamplicol evaluate artifacts/loop_generate \
  --set evaluation.phase_space.points=4 --set evaluation.phase_space.sqrt_s=2000

check draws its own points ([check] points, seed, sqrt_s).

Saved virtual artifacts¶

The artifact selects the virtual execution lane; loading it does not require repeating its loop coupling orders. Supply the renormalization scale squared:

pyamplicol evaluate artifacts/virtual --process gg --momenta points.json \
  --mu-r2 1000000 --arithmetic double --r2-strategy model --json

--arithmetic accepts double, double-double (DoubleFloat) or arbitrary. --arithmetic arbitrary without --precision runs at the default arbitrary-precision digits (500, the native policy’s DEFAULT_ARBITRARY_DIGITS); --precision 70, for example, sets the digits, and a number given is never overridden. These choices apply before model parameters are bound. Without an explicit arithmetic choice, the existing precision convention applies: 16 digits (the default when unset) selects double; other requested precisions select arbitrary precision. DoubleFloat is always selected explicitly.

--loop-reduction {auto,ninjars,tirust} selects the reduction backend for the evaluation, overriding the artifact’s default (generate --loop-reduction records that default): auto takes TIRust for a loop-induced and NinjaRS for a Born-interfered process, falling back to NinjaRS with the reason recorded where TIRust cannot serve the call; on TIRust a point it refuses or fails is evaluated again on NinjaRS (the per-point fallback, recorded in that point’s lane diagnostic), and in double-double and arbitrary precision each point it serves is guarded by a rotation re-test in the evaluation’s arithmetic: a point whose estimate exceeds the target (never below 1e-5) fails with the reason (the estimate is in the lane’s reduction record, guard_estimate; Python API, “Near-planar NinjaRS hazard”); a binary64 fallback point is served unguarded; ninjars and tirust request one backend without a fallback or guard (tirust serves every arithmetic; ninjars without stability checks was exposed to that hazard until NinjaRS’s conditioning bound, 71eddb15); an explicit backend that cannot serve the call is refused. --reduction-target X sets TIRust’s target accuracy (the relative accuracy of each point’s result, default 1e-5; it sets the calibrated acceptance of TIRust’s checked method choice and, never below 1e-5, is the fallback guard’s threshold). --kinematics-improvement VARIANT (z-shift, rescaling, projection or off; default z-shift, MadLoop’s ImprovePSPoint = 2 with its fallback to 1, finished by the projection where MadLoop leaves the point inexact) and --[no-]kinematics-improvement-binary64 (default off) set the improvement of the input points to exact conservation and on-shell externals before a double-double or arbitrary-precision evaluation (binary64 only with the switch); the JSON output’s lane diagnostics carry the per-point record (kinematics; Configuration). Both are evaluate, profile and check flags (for check, below) and the run card’s [evaluation] kinematics_improvement / kinematics_improvement_binary64; an unknown variant is refused with the native policy’s one refusal text when the configuration resolves. --reduction-unchecked (default off) reduces without the backends’ own acceptance and refusal checks: TIRust’s gates and method choice select the method without re-checking its values, plain Passarino-Veltman at gate 0 serves what they refuse, NinjaRS runs with zero stability thresholds (its box mu-expansion’s conditioning bound stays active); only points without a finite value or refused by that bound still fail, auto keeps its backend choice and its fallback acts on those only. It is a timing and benchmark mode with no accuracy certificate; the lane rescue still serves the lanes the unchecked backend refuses (--no-lane-rescue, evaluation.lane_rescue = false, turns it off; Python API, “Lane rescue of refused reduction lanes”) (the measured accuracy per process: Python API, “Unchecked reductions”). The JSON output’s lane diagnostics name the requested and effective backends, the reason, the fallback, the target and the unchecked setting. A loop-induced artifact (contribution: "loop-induced" in the JSON, empty born_values) takes --poles all or none only.

Use --mu-r2-file scales.json for one positive scale squared per point, instead of --mu-r2. A scale file such as [1000000, "900000.0000000000000000001"] accepts JSON numbers or strings. Virtual momenta, parameter and scale files preserve decimal digits before native arithmetic conversion. Parameter pairs [real, imaginary] also preserve their exact inputs.

Human output lists every Born and virtual squared coupling order and all three coefficients, with contributing Born–loop pairs and per-point diagnostics. JSON adds explicit epsilon_powers: [0, -1, -2], coefficient names and shape metadata; high-precision values are decimal strings. Neither format silently sums orders or divides by the Born result. A successful lane can still report accuracy_established: false.

--orders splits a virtual evaluation by squared coupling order: one evaluation (Runtime.evaluate_orders, a VirtualOrderEvaluation view), every sector’s Laurent coefficients and every Born order apart as above, followed by a separately titled table of the explicit sums over the orders (JSON: evaluation, orders, born_orders, sum_orders, sum_born_orders). The sums are named and printed apart; nothing is summed silently.

The precision-rescue options (--stability-higher, --stability-relative-tolerance, --stability-absolute-tolerance, --verify-successful, card section [evaluation.stability]) were removed with the legacy loop engine, the only one that served them; naming one is refused with the reason. v2 evaluations return stability estimates (--stability-rotations, --stability-reduction-direction, --stability-rescaled) and leave escalating --arithmetic to the caller.

--on-failure best-effort is the default (since 1.0.3): a point that no configured alternative accepts (the reduction backend’s own acceptance checks, auto’s per-point fallback, the last rescue level) is returned with its best available value, the unchecked reduction’s, its refusal and its uncertainty, status best-effort (never a success; yellow in the status column of the evaluation diagnostics), and a point without any value as an unavailable row. Nothing is printed per point: the human tables end with one dim summary line (N captured warning(s) (...); see --json / result.warnings), and --json carries statuses and warnings (per kind: source, kind, first message, count, where, point indices; each lane’s reduction.best_effort record holds refusal, uncertainty, source, backend_deviation and gram_conditioning). Wherever a relative uncertainty or stability estimate above 1 is shown to a human (the evaluation’s stability table, lane details, failure and cause lines) it reads >1; --json, the samples file and the returned records keep the number. --on-failure return preserves successful points and returns an unavailable whole-point row for each numerical failure (no best-effort evaluation): null in JSON, with its failure diagnostics. --on-failure raise (the default before 1.0.3) stops at the first such point. generate and check return the known, benign dependency log events they trigger (see the release notes) in their result’s warnings, shown as the same one dim line, instead of printing them. An actual zero remains a numerical zero. A scale at which a counterterm coupling is not finite in the chosen arithmetic (e.g. 1e-400 in binary64) is such a failure of its own points. Malformed inputs (a non-positive --mu-r2) and unsupported capabilities remain errors for the whole call. Both inclusive and --resolved evaluation use this option; resolved axes follow the artifact’s retained layout. It requires virtual evaluation and is rejected on other commands, including profile; configuration inspection can still display it.

--threads N sets the native threads of the artifact’s load and of every evaluation (evaluation.threads; default: RAYON_NUM_THREADS, else every core; precedence --threads > RAYON_NUM_THREADS > every core); the values do not depend on it. Every runtime option of this section can also come from a runtime-options file, a run card with only an [evaluation] table (--card examples/data/runtime_options.toml; a flag overrides the card’s key; the keys and their flags: Configuration).

Only strategies and observables present in the artifact may be selected.

Correlated requests¶

Supply a JSON object of labelled numerical requests to evaluate colour and spin correlations together over the entire point batch:

pyamplicol evaluate artifacts/virtual --momenta points.json --mu-r2 1000000 \
  --correlated-requests requests.json --on-failure return --json

{
  "physical": {"color_correlation": "born", "spin_vectors": {}},
  "joint": {
    "color_correlation": "born",
    "spin_vectors": {
      "3": ["0", ["0.8", "-0.16"], "0", ["-0.6", "0.12"]],
      "4": ["0", "0", ["1", "0.2"], "0"]
    }
  }
}

Request labels become output keys. color_correlation defaults to born; use stored colour-history IDs for other operators. The supplied vector-leg set must be a class declared in the artifact. Leg keys use public one-based labels, and each value is a four-vector or one four-vector per point. Components may be exact real numbers, strings, or [real, imaginary] pairs. Vectors are used literally, without normalization or projection. Unknown fields, duplicate JSON keys and colliding leg spellings such as "3" and "03" are errors.

Missing or null spin_vectors inherits the runtime’s default; a fresh CLI runtime has no replacement sources. {} explicitly selects physical helicities. One entry requests one observable; multiple entries use the existing grouped runtime call, preserving each label and its independent failure mask. Human output prints each result under its label; virtual JSON retains every coupling order, Laurent coefficient and diagnostic, including unavailable rows.

Tree artifacts use the same request file, without virtual scales, R2, stability or partial-return options. Their correlated API defaults to arbitrary precision; --arithmetic double-double selects its existing DoubleFloat path. --precision and --helicity follow the underlying correlated API. Virtual requests inherit the arithmetic and stability policy selected at load time.

--resolved and --color-flow cannot be combined with correlated requests: the grouped API returns contracted observables. Generation-time --correlators declares capabilities; evaluation-time --correlated-requests supplies numerical values and selects among those capabilities.

Profile¶

The profiler measures the same optimized total path as Runtime.evaluate():

pyamplicol profile artifacts/pp_zjj \
  --process 'd d~ > g z g' \
  --momenta data/pp_zjj_momenta.json \
  --target-runtime 1.0 \
  --batch-size 128 \
  --color-flow 1 \
  --precision 16

It calibrates repetitions, keeps at least the requested independent sample count, and reports uncertainty. Ctrl-C during sampling preserves completed blocks and prints a result marked partial. See Profiling and Benchmarking for metric meanings and selector-aware profiling. If both profile selector axes are omitted, the stored LC layout supplies a deterministic optimized selector; explicit non-hot shapes are retained and produce at most one pre-loop warning per loaded process.

A one-loop (v2 virtual) artifact is profiled on both reduction backends side by side (TIRust and NinjaRS, the process type’s default first: TIRust for a loop-induced process, NinjaRS for a Born-interfered one); --loop-reduction tirust|ninjars profiles that backend only (auto: the default backend alone, with its per-point fallback). A backend that refuses the process is shown as refused with its typed reason; the command still succeeds. On an expensive process only the default backend may be profiled, and the runtime timing may run without its reference (rules A and B under “Time budgets” below; --all-backends and --ground-truth keep them). What each part runs, from the reduction checks and the lane rescue to the stability checks, and how to switch each off, is summarised in The stability machinery, end to end. What is measured:

Both parts use the flat phase-space points of [evaluation.phase_space] (RAMBO on diet, the product’s flat generator: beams along +-z in the centre-of-mass frame, the external masses of the artifact’s validation point; point i from seed + i; --seed and --sqrt-s set evaluation.phase_space.seed and sqrt_s) unless --momenta gives the timed points; the runtime and the stability points are drawn separately from the same seed.

Time budgets. Three rules set the counts of a loop profile, in this order (the header’s counts row names the one that applied and what the profile took):

  • --completion-time DURATION (benchmark.completion_time; seconds, or a text such as 90s, 10m, 1h30m): the whole command, as you wait for it (interpreter start, load, measurement, every backend’s runtime timing and reference pass, the stability run on its workers, the statistics and the per-sample records of --json or --samples-output: their time is part of the plan), aims at that wall time, within about a factor 1.5 either way. It overrules every count and size, on the command line and in a run card alike (--target-runtime, --minimum-samples, --batch-size, --warmup-runs, --stability-points; one notice line says which; the plan sets them all): a short measurement first (its own phase: per backend the cost per point of binary64 and of the reference, each from one point and, when a full SIMD chunk costs at most 2 s at that price, from one chunk), then the plan: the runtime timing first (a stable median, at least the default 10 s when the time affords it, at most half of what is left when --stability is asked for too), the reference pass bounded within each backend’s share, the stability run admitting chunks while they end by the deadline. Later phases are re-planned from what is left. The minimums are never undercut: one timed call of one filled chunk per backend for the runtime, five stability points per backend; when they alone exceed the requested time a warning says so as soon as the measurement is back, with the time the whole command then takes (the header’s counts row states the same number), and the minimums run.

  • the counts given on the command line or in a run card: honoured as given. A value stated in a run card counts as given even when it equals the default (n_core = 10, ground_truth = "double-double"): leave a setting out of the card to keep its default behaviour. A --target-runtime given alone is each backend’s timed binary64 budget (its start-up and warm-up outside it, the reference pass’s budget the same on top), and the counts are chosen from it: one warm-up, the largest batch whose five calls fit it, the minimum calls and more while it affords them (not the default batch and calls as if given).

  • neither: the default budgets, 10 s for the runtime timing of all backends and one minute of work per --n_core worker for the stability run (about a minute of wall time whatever --n_core: more workers, more points). On an expensive process whose minimums exceed them by more than a factor 1.5 the same warning says so, with the time the minimums take. The measurement times only what can change the counts: a backend whose share of the 10 s (its start-up excluded), less the reference pass’s quarter of it, affords no more than its binary64 warm-up gets the minimum counts whatever its reference costs, so its reference is not timed there (its runtime timing’s untimed reference call measures it); when loading the artifact alone takes a backend’s share, every backend gets the minimums and there is no measurement phase at all (nothing is evaluated before the runtime timing, whose warm-ups measure the costs; a notice names the load time, and whether the minimums exceed the budget, with their time in the counts row, follows from the costs the timing measured).

    On an expensive process the profile runs less. This happens when its minimums exceed the budget by more than a factor 1.5 (the counts row’s rule, start-ups aside). The budget is the runtime timing’s (10 s for all backends by default, or --target-runtime per backend), plus the stability run’s minute with --stability; with --completion-time, what is left of it. Two rules then apply:

    • Rule B, the reference of the runtime timing (without --stability): when the runtime minimums of all backends with their reference points (one untimed and one timed point each) exceed the budget, no reference point runs and the (dd xN) / (arb(D) xN) multiplier is not shown, as with --ground-truth none. An explicit --ground-truth (any value, also double-double, on the command line or in a run card) keeps it. With --stability the reference always runs (the true digits need it); the runtime row then takes its multiplier from its own reference pass, never from the stability run’s.

    • Rule A, the backends (with or without --stability): when the default backend alone, for everything asked (its runtime minimum with the reference as rule B decided, and five stability points with their reference), still exceeds the budget, only the default backend is profiled, in both tables. --all-backends profiles every backend whatever the budget, --no-all-backends only the default one, --loop-reduction one backend. With one backend and an arbitrary-precision ground truth, every reference is certified by its own checks (there is no second reference to agree with).

    Counts given (--batch-size, --minimum-samples, --warmup-runs, --stability-points with --stability) are honoured and nothing is left out; given with --target-runtime, the counts win. The rules decide on what this run has measured so far, and again each time a new cost is measured. They leave something out only when a lower bound of its cost already exceeds the budget (a chunk counts at least one measured point, a warm-up one point, a reference that warms through the warm entry the entry’s measured seconds), so a decision is never taken back. Rule B is judged on the sum over all backends, so a backend’s dear reference counts even when the default’s is cheap, and its verdict holds for every backend (all multipliers or none). Rule A never counts a reference that rule B could leave out. A previous profile’s costs set the ETAs only, never a verdict. A notice says what was left out, and the counts row repeats it (“TIRust not profiled (–all-backends)”, “no dd multiplier (–ground-truth)”).

    The stability run starts no more worker processes than the memory holds: at most three quarters of the memory available when it starts, at one worker’s resident size as this run measured it (the profile’s own process after loading the artifact and measuring every backend, or the load plus each backend’s increase in its runtime timing’s process); the plan, its ETA and rule A count those workers. When a stability task holds several points (a point cheaper than a task’s work), the first worker runs its first task alone and its own peak sets how many follow. Fewer workers than --n_core then run, said in a notice and in the counts row (“stability on 3 workers (memory: 36.5 GiB each, 3/4 of 150.0 GiB available)”). A --n_core given (command line or run card) is honoured, with a warning when its workers do not fit. The runtime timing runs one process at a time.

Loading, process start-up, warm-up calls and the reference pass’s minimum are outside the default budgets by nature; they are visible phases with their own estimates. The reference pass is part of the budget of the phase it serves. Where the runtime offers a warm entry (it builds what a carrier’s first evaluation builds, without evaluating a point), the binary64 timing of the optimistic pass and the reference pass warm through it instead of their untimed warm-up, unless that warm-up is known to cost less than the entry (the entry’s cost from a previous profile, else the first-call overhead the measurement saw); while rule B may still drop the reference, the reference warms up with its untimed point. --checked never uses it. The timed calls are the same warm passes, and the runtime setup row says “after a warm entry” (--json: prepared_seconds, the entry’s time). On an expensive process the binary64 warm-up is one point (when a full call would cost more than 2 s; else one full call), and a stability task holds about 4 s of work: a point that costs more is a task of its own, so a few expensive points spread over the workers instead of running one after the other.

Monitoring. On a terminal the profile shows three live lines: the whole command (elapsed, its ETA, ~ while it rests on a prior, the budget left with --completion-time, the process tree’s resident memory and busy cores), the current phase (calls or points done of the planned ones, a bar, its ETA, counted down every second and never 0 while work remains) and what is running right now (the call and how long it has run against its expected cost; “no progress for …” in the warning colour once a call runs three times past it) with the current best estimates: per backend its binary64 time per point and the running reference multiplier (N/A, muted, until a timed call is back), or the stability run’s points done and flagged counts. Every finished phase leaves one line with what it cost, the statistics and per-sample records of a large stability run included; a large --json dump says on stderr that it is being written. The whole command’s ETA is there from the first second: a profile remembers the artifact’s measured costs and its total for the same settings (in the pyAmpliCol cache, beside the generation history; written only when progress is shown), and the next one starts from them; without a previous profile the --completion-time budget stands until the first measured call, then a provisional plan from the costs known so far (the other backend’s binary64 cost, the reference from a per-backend multiplier prior) until the measurement is over. The tables fit the terminal when it is narrower than 100 columns (headers wrap at their spaces, numbers never break; --json and --progress log are unaffected). --progress log prints one line per event and a heartbeat at least every 10 s; --progress off prints nothing.

Runtime. Every backend is timed on one core, the cost one Monte Carlo worker pays: in its own spawned process whose thread pools all run one thread (rayon’s, used by every native pool, and any BLAS/OpenMP pool; --n_core is the worker count of --stability only), on batched calls whose SIMD lanes are filled. Every time the runtime tables print is a time per phase-space point on that core: a call’s wall time over its points (cpu_per_wall in --json, the process’s CPU time over the timed calls’ wall time, is at most about 1 and says how much of the core the host left it). With counts given, --warmup-runs untimed calls come first, then at least --minimum-samples timed calls, more until they add up to --target-runtime seconds, each of --batch-size points (up to 128: eight whole 16-point binary64 SIMD chunks); under a time budget, one untimed call, then the largest batch of whole chunks that affords a stable median within the backend’s share, at least one timed call, every call on a new batch of distinct points: without --momenta, the flat points from the seed on (seed and energy as above; call k, warm-ups counted, takes the points from k x --batch-size on, so every call has the same points on every backend); with --momenta, its points in order, cycled when there are fewer. What is timed, which the table header names: binary64, finite part only, one fully optimistic pass per point (the same pass as the reference multiplier’s, below): each backend’s unchecked reduction alone (no auto fallback), no stability checks, no rescue, no best-effort re-evaluation of a refused point (a point without a value is counted failed); a reduction lane the unchecked backend still refuses is rescued inside the timed call (the header says “refused lanes rescued”; --no-lane-rescue times pure binary64 calls, such points then without a value). --checked (benchmark.checked = true) times the checked mode instead: the backends’ own acceptance checks, a refused point returned with its best-effort value and timed as such (its unchecked re-evaluation and its uncertainty’s checks included), the default backend as auto with its per-point fallback; the header then says “checked reduction”. --reduction-unchecked (evaluation.reduction_unchecked) loads the runtime unchecked, which also makes the stability run’s binary64 calls unchecked; it cannot be combined with --checked. The first table gives each backend’s name (*: the default backend of the process type), its time per point (median call), the fastest and slowest call, the ratio to the fastest and its peak RAM; with --checked a best-effort column appears when some timed points were served best-effort and a lanes column when points were served by more than one backend; a failed column appears when points got no value. Under the table, after a --- line, the failed or refused points are listed per backend and cause, most frequent first, in the form <count> (<fraction> %) <backend> | <kind>: <cause> (causes grouped with their numbers masked; also in --json as failure_causes); nothing is printed when nothing failed. The kind lane rescue counts served points whose refused reduction lanes were reduced again in a higher carrier (reduction lanes rescued in <carrier>; python-api.md, “Lane rescue of refused reduction lanes”); their time is in the timed calls (--json: each runtime row’s lane_rescue_points and lane_rescue_reasons). The second table gives the time per point in each stage group (trees: the native trees and counterterm kets; dressing: seeds, factors and dressing of a Born-interfered process, the dressing of a loop-induced one; scatter; reduction; rest: every other stage and the untimed remainder), read from the native executor’s always-on stage reports of the same timed calls, with each backend’s share (and a bar per group) and the ratio between the two backends: the shares of the timed calls’ total time applied to the time per point, so the stages add up to it (rest is what the native stages do not attribute: Python’s part of the call and the native work outside the named stages). --mu-r2 sets the scale (default: per point the squared invariant mass of its initial state).

More threads per call. --runtime-threads N (benchmark.runtime_threads, default 1) times each backend’s calls with N native threads working inside each call: its process’s thread pools at N threads (the binary64 calls and the reference pass; the timed runtime is loaded with threads=N, the mechanism of evaluate --threads, so its load runs on N threads too; evaluation.threads of a run card does not change a profile), the calls still one at a time, never several batches in parallel; N is at most the usable cores (a plain line says so when it is reduced). The time per point is then the wall time of a call with N threads working over its points: it is not the cost of one core, and a Monte Carlo run that gives each worker one core should use the default. The header says on N threads; next to each time a muted (xS vs 1 thread) gives the gain, from a short one-thread timing of the same calls after them in the same process (the runtime reloaded at one thread; a quarter of the binary64 budget, at least one call; one_thread_seconds_per_point in --json). peak RAM is the N-thread process’s, measured before that timing, and cpu_per_wall approaches N. The stability run is not affected: its --n_core workers run one thread each; with --stability the option only changes the runtime timing. The cost measurement and the plan of the time budgets stay at one thread (the stability workers’ cost; the N-thread calls then fill their budgets with as many calls as they afford).

peak RAM is the memory to expect for each Monte Carlo worker evaluating the matrix element on that backend: every backend is profiled in its own spawned process that loads the artifact and runs that backend’s warm-up and timed calls only (so no backend’s figure holds the other’s prepared state), and the cell is that process’s peak resident set size over those binary64 calls, at the runtime setup’s points per call, on one core (one thread per pool), before the reference timing. On Linux it is the kernel’s high-water mark (VmHWM), reset when the calls start (/proc/self/clear_refs); on macOS and the BSDs only the process lifetime’s peak is known (getrusage ru_maxrss): it is the calls’ peak when they raised it, else the cell shows the bound, <= 2.21 GiB (the worker’s load reached more than the calls). --json keeps the start value, the increase, the scope and the method (peak_memory).

Next to the time per point, (dd x15) is the reference multiplier: N is the time per point of one fully optimistic pass of the same backend in the reference precision (--ground-truth, below; dd double-double by default, arb(D) arbitrary precision at D digits) over the displayed time per point, both on the same core. The optimistic pass is one evaluation per point and nothing else: the unchecked reduction of that backend alone (no auto per-point fallback or guard), no stability checks, no rescue, no best-effort re-evaluation. It runs after the binary64 calls in the same process as its own phase: one untimed call of one point (none with --warmup-runs 0; the first call of a carrier builds what it builds lazily, its batch size no longer matters), then calls of one SIMD chunk (16 points: no padded lane in any carrier), at least one, more while the next fits its budget (a quarter of the backend’s runtime share, --target-runtime with counts given); when the budget affords fewer than 16 points at the cost the untimed call measured, its calls take as many as it affords, at least one point, and the header says how many reference points the multiplier comes from. Its cost is therefore bounded however expensive the carrier (before: one untimed and at least --minimum-samples 16-point calls, ~25 minutes of silence on a 7-point process). Call k takes the first points of the binary64 timing’s batch k; N is its median call’s time per point over the binary64 median call’s: the same pass in both, so N compares like with like (with --checked the denominator is the checked time). In colour the time is bold (green for the fastest backend) and the whole parenthesis is muted (bright black), in both tables; --color never prints the same text without escapes.

The multiplier has one decimal below 10 and none from 10 on. A reference that gives no value at any timed point leaves the time alone. The reference timing’s calls, points, fastest and slowest call, peak RAM and points without a value are in --json (reference, with its arithmetic and digits); such points are listed under the table as ... in double-double (or ... in arb(D)) causes, counted over the reference’s points. A tree artifact’s profile reports peak RAM as a summary row (its runtime profile is binary64 only, in one process, its pools at one thread). --fields-description-help explains every column, with how this run measured peak RAM.

Ground truth. --ground-truth (benchmark.ground_truth) selects the reference of both tables: double-double (dd, the default) or arbitrary precision, arbitrary (arb) at the default arbitrary-precision digits (500, loops.v2.reduction.default_arbitrary_digits(), the native policy’s DEFAULT_ARBITRARY_DIGITS) or arbitrary:DIGITS (arb:DIGITS). It is the stability run’s truth and the precision of both tables’ multipliers, and the labels follow it: the header’s ground truth row, (arb(500) x210), “Stable digits of binary64 vs arb(500)”. The values judged are binary64’s either way; a point whose reference fails is “no ref.” as before. In arbitrary precision the stability run cross-checks each point’s references between the backends: a reference that agrees with another backend’s to 2^-106 relative (binary64’s unit roundoff squared, the accuracy of the double-double truth) is trusted as it is; any other valued one, or the only one (the other backend failed or refused), is evaluated again with the recommended stability checks (RECOMMENDED_CHECKS) and counts as one whose reference fails when its estimate exceeds binary64’s unit roundoff (2^-53: a reference exists to resolve the stable digits of a binary64 value down to their cap) or when two such checked references still differ by more than it (their estimates are contradicted); its cause says which. So a wrong value with status success does not become the truth. The cross-check compares the two reductions and their master-integral code; the numerators, the R2 and counterterm parts and the assembly are common to both backends (as they are to the binary64 value judged), and TIRust’s masters are generated from the same OneLOop expressions as NinjaRS’s. With one backend profiled (or the other refused) every reference is evaluated once, with the checks. --json records each reference’s certification (reference_certified). The runtime table’s multiplier stays the time of one optimistic pass; the stability table’s reference time includes the checked evaluations. Arbitrary precision costs far more than double-double; its runtime timing is bounded as the double-double one is. --ground-truth none runs no reference at all: no reference pass (the runtime table shows the time alone), and the stability run evaluates binary64 with its checks only (much faster) and reports what the estimates say in an estimate-only form: the estimated digits at the percentiles and the default checks’ flagged and best-effort counts with the binary64 time, without the truth-based columns; the header says none (estimates only) and the JSON’s ground_truth {"arithmetic": "none", "label": "none"}.

Measured precisions. --measured-precisions (benchmark.measured_precisions, a list; on the command line space- or comma-separated, --measured-precisions double dd arb:60) names the precisions whose stability the stability run measures, each its own pair of tables in the order given; the default is binary64 alone (today’s tables). An entry is binary64 (double, b64) or what --ground-truth accepts (double-double/dd, arbitrary/arb, arbitrary:DIGITS/arb:DIGITS). Each entry’s points are evaluated as binary64’s are, in its arithmetic: the default checks (one default rotation; on TIRust’s points also the rescaled reduction-direction check), a refused point served best-effort, lane rescue as that arithmetic has it (--no-lane-rescue turns it off). An entry below the ground truth is read against it (“Stable digits of double-double vs arb(60)”): its true and estimated digits capped to its own range (double-double -log10(2^-106) = 31.91, arbitrary precision its digits) and to what the ground truth certifies (its range; an arbitrary-precision truth its cross-check’s 2^-106, or on a point where the backends’ references agree closer the agreement they reach), the title adding “capped at what the ground truth certifies (at least D digits)” when that is the lower. The ground truth’s own precision has its estimates-only tables (“Estimated digits of arb(60) (the ground truth)” and “Default checks, estimates only, arb(60)”): its points are evaluated in it once, with the default checks, and that evaluation is also the reference of the lower precisions (its unrotated value is the plain reference evaluation’s bit for bit, verified on g g > g g g in double-double and arb(60); a best-effort or failed point has no reference, as before; the certification of an arbitrary-precision truth is unchanged; with one backend and an arbitrary-precision truth its references stay the checked evaluations). A ground truth not listed gets no table and no checks beyond its certification above (with an arbitrary-precision truth the cross-check between the backends and the checked re-run of a reference it does not certify; with one backend one checked evaluation per point). An entry above the ground truth (or listed twice) is refused before any work; with --ground-truth none every entry is estimates-only. A precision not listed is not evaluated: without binary64 in the list the stability run has no binary64 stream (stability is then empty in --json) and the runtime no binary64 calls, except binary64’s runtime worker when another listed precision’s table shows the ground truth’s multiplier and the truth itself is not listed (the multiplier pass runs in that worker); binary64’s counts are still the start of the other precisions’ calls. Each precision’s failure causes are under its own tables. The precisions given are honoured; the stability plan and its ETA count each extra stream at a lower bound of its point (a checked binary64 point below the ground truth, the plain reference point for the ground truth’s own) until the run measures it, and the default budget’s deadline admits points at the measured costs of every stream. The scope rules (A and B above) count them by lower bounds too: binary64’s calls only when listed, every other precision’s stream at least two binary64 points in the runtime timing (its measuring call and one timed call) and one binary64 point per stability point, a listed ground truth as the reference it is (in the runtime timing its stream runs after binary64’s rows, so until then rule A sees it at one binary64 point per call and rarely leaves a backend out for it, more output than asked, never less); the stability plan prices a listed ground truth’s stream at its checks’ evaluations per point (the point and each rotation of a plain reference point); the whole command’s ETA counts each precision’s runtime calls (its measuring point and its budget) until they run, and --completion-time keeps their estimates out of binary64’s share and gives each the time left when it starts. With --runtime, every entry other than binary64 also gets its own “Runtime per reduction backend, ” and “Time per point and stage, ” tables, in the order given (the ground truth’s own precision too: timing needs no truth; with a list given, binary64’s runtime and checks tables are titled “, binary64” as well): per backend the same optimistic pass as binary64’s in that arithmetic, in a process of its own (one core, or --runtime-threads), its stage groups from the native stage reports of those calls and its peak RAM. It starts from binary64’s counts and budget for that backend (--target-runtime is each backend’s timed budget per measured precision); its one-point warm-up call (untimed) measures its cost, and its batch falls to the largest power of two that its calls fit in that budget, down to one point, that call its warm-up (a --batch-size given is honoured: every call holds that many points). A wider carrier’s time per point depends on the points per call (double-double on g g > g g g, NinjaRS: 0.69 s at one point, 0.57 s at two, 0.45 s at 16), so it compares with the multiplier pass’s (one point per call where it is dear) at the same batch. Its time carries the ground truth’s multiplier against it, (arb(60) x1.1), none on the ground truth’s own table. When the ground truth is listed its stream is timed once: it is the multiplier of binary64’s table and of the others (no separate multiplier pass), and rule B leaves it in (a precision given). In --json its rows are runtime_measured (each its precision record and runtime rows as runtime), absent by default. In --json the other precisions’ rows are under stability_setup.measured_precisions (each entry its precision, estimates_only, digits_cap, capped_by_truth and stability, the same rows as stability; binary64’s entry stability: null, its rows where they always are); the key is absent with the default. The per-sample records (--json, --samples-output: its measured_precisions) of a wider precision hold its value and sectors as the exact decimal text of its carrier’s value; every precision’s records also carry estimate_digits_uncapped and true_digits_uncapped.

Stability. Over N flat points (benchmark.stability_points / --stability-points; by default as many as one minute per worker affords, at least five; with --completion-time what is left of it; drawn with evaluation.phase_space’s seed and energy), evaluated in parallel on benchmark.n_core / --n_core (also --n-core) worker processes (default 10, at most the usable cores; 1 runs in-process; each worker loads the artifact once and runs one thread per pool; the tables do not depend on the worker count), with a progress display of the points done per backend and precision and an estimated time to completion; Ctrl-C stops the run and prints the tables of the points evaluated so far with a one-line notice (stability_setup.requested, measured_points, interrupted in --json; exit code 130), a second Ctrl-C aborts. The runtime timing runs before the pool, one process per backend. Each backend evaluates every point in pure binary64 with the default checks: one default rotation on a point NinjaRS serves, one default rotation and the rescaled reduction-direction check on a point TIRust serves (per point under --loop-reduction auto: a per-point NinjaRS fallback point keeps the NinjaRS set); evaluation.stability_checks replaces them when set, unchanged per backend (the rescue’s own check set, a fixed Euler rotation plus the rescaled-reduction check on every level, is not what is measured here) and again in double-double on the same backend in the reference precision (--ground-truth; double-double by default), the reference. Following the measure of MadLoop (arXiv:1103.0621, sect. 3.4) and MadGraph5_aMC@NLO (arXiv:1405.0301, “Checks, stability, and recovery of numerically-unstable integral reductions”), the number of stable digits of a value v against a reference r is -log10(|v - r| / |r|), read on the finite part of the total (the sum over the squared-order sectors; the poles are not computed) and capped to binary64’s range [0, 15.95]:

  • true digits: the binary64 value against the reference re-run (its sectors summed exactly, the error formed in rational arithmetic);

  • estimated digits: the binary64 call’s own stability estimate (its absolute finite-part errors summed over the sectors, over |total|).

Refused and failed points are part of the distribution. A point the backend’s own checks refuse in binary64 is measured with its best-effort value (the unchecked reduction’s, what the default on_failure returns, status best-effort; since 1.0.3) at its true digits, its estimate being the call’s checks’ estimate of that value; it is never accepted, so it always counts as flagged. A point whose refused lanes the lane rescue served (cause kind lane rescue) is measured like an accepted one, its estimate covering the mixed total. With the default checks a TIRust point’s value can differ, at a rescued lane’s rounding, from a one-rotation run (a lane refused only in the reduction check’s frame is rescued in both frames). Lanes a backend accepts are never rescued, however inaccurate: such points are measured (and flagged by their estimate) as before (on flat 2 -> 6 gluon points 10 of the 23 points NinjaRS accepts have an estimate above 1e-5, 3 above 1). A point with no binary64 value at all (“no value”) counts 0 true digits (the worst end of the ranking) and has no estimate. A point with a binary64 value whose reference failed has an unknown truth and is left out (shown as “no ref.”). The measured points (N in what follows) are all others.

The measured points are sorted by true digits from worst to best. At the percentiles 1 per mil, 1 %, 10 %, 50 % and 100 % the table shows the true digits of the point of rank floor(p N) (1-based; the 50 % row is the median, the lower middle point for an even N; the 100 % row the best point), and over the class of points of rank floor(p’ N) < rank <= floor(p N) (p’ the previous percentile, 0 for the first; the classes add up to N) the min, median and max of |estimated - true| and the median of estimated - true (positive: the estimate is optimistic), both over the class’s points with an estimate. A class holds floor(p N) - floor(p’ N) points, so the table shows no count (--json keeps each class’s count and failed); a class with points without a value says so after its digits, 0.00 (2 failed). At small N a class can be empty (-; the table prints the N a populated class needs: 1000 measured points for the 1 per mil class, 2 for the median, 1 for the 100 % row).

A second table compares the default checks with the truth, per backend: the measured points, those served best-effort / without a value in binary64, the points flagged unstable (estimate above the default target 1e-5, per sector, the metric the rescue reads, or a binary64 failure, which the result reports and so detects), the flagged points that are truly inaccurate (true relative error above the target, or no binary64 value) and the truly inaccurate points not flagged (“missed”), and the wall time of its binary64 calls (with their checks, summed over the workers) with how many times longer its reference calls took in total, 128 s (dd x1.8) (on a second line when the table would pass the line width; each precision’s points, total and time per point are in --json, precision_timing). Every worker loads the artifact and makes one untimed call per backend and precision before any timed one, so start-up costs stay out of both totals, and the points go in tasks of whole binary64 SIMD chunks. The binary64 calls include their stability checks (the default checks evaluate each point again rotated, and re-reduce TIRust’s points in the rescaled frame) while the reference evaluates each point once (with an arbitrary-precision ground truth, plus the checked re-runs of the references the cross-check did not certify, or with one backend one checked evaluation per point; each worker’s first checked call is untimed), so this multiplier is not the cost ratio of one evaluation: that is the runtime table’s (dd xN). No rescue runs: the statistics are those of pure binary64; the reference re-run is the reference only. When a backend served points best-effort, a third table shows how accurate those values and their uncertainties are: per backend the number of best-effort points, their true digits (min / median / max), the median digits of their uncertainty, the median |uncertainty - true| digits and how many uncertainties cover the true error (true relative error within the uncertainty). The uncertainty is the best-effort record’s (VirtualBestEffort.uncertainty: the card’s checks together with the recommended checks, a rotation and the rescaled reduction-direction check), not the card’s own estimate shown in the first table. Digits are coloured red below the target’s digits (5 for 1e-5), yellow in the lower half of the margin between the target’s digits and binary64’s 15.95 (a display convention) and green above. The footnotes under the tables state these definitions; every table fits a 100-column terminal (a cell’s annotation, such as “(+4 no ref.)” or the multiplier, goes under its value when one line would not fit) and the footnotes wrap to the terminal width.

Colours follow --color auto|always|never; --json carries every number uncoloured (loop_profile.LoopProfileReport: runtime per backend with its benchmarking.VirtualProfileResult profile (seconds_per_point, low, high, stages, reduction, unchecked (whether the timed calls reduced unchecked: true for the optimistic pass, false with --checked, whose best-effort points do not change it), batch, samples, failed_points, failure_reasons, best_effort_points (with --checked; 0 in the optimistic pass), peak_memory with peak_rss_bytes, start_rss_bytes, increase_rss_bytes, scope and method, threads (the native threads of the timed calls: 1, N with --runtime-threads N), cpu_per_wall (about 1 on one core, approaching N on N threads), with --runtime-threads N > 1 one_thread_seconds_per_point and one_thread_calls (the one-thread timing of the same calls), and reference: its arithmetic, digits, seconds_per_point, low, high, batch, points, samples, warmup, failed_points and peak_memory), ratio, requested and refusal; ground_truth (arithmetic, digits, label); stability per backend with the per-point true_digits and estimated_digits of the measured points, precision_timing (per precision, binary64 and the reference’s arithmetic, double-double or arbitrary with its digits: points, seconds and seconds_per_point), per_point (every flat point’s index, status measured / binary64-failed / reference-failed, digits and failure reason), the percentiles rows, the flag counts and the failures; stability_setup), the plan (its rule, the counts chosen per backend, stability_points, expected_seconds, budget_seconds, feasible, minimum_seconds, overruled, and the counts the runtime achieved) and the profile’s wall seconds.

Every sample in --json. With --stability --json the report carries everything the run collected, point by point, as compact columnar tables (about 0.9 kB per point with two backends: 87 MB for 100 000 points; write it to a file with --json > profile.json). Each table is {"fields": [...], "rows": [[...], ...]}, one row per point (in Python: [dict(zip(t["fields"], row)) for row in t["rows"]], or pandas.DataFrame(t["rows"], columns=t["fields"])). stability_setup.samples holds every point’s inputs: index (point i is drawn from stability_setup.seed + i by the flat generator at sqrt_s), momenta (the binary64 four-momenta E, px, py, pz of every leg in the process’s order) and mu_r2. stability[i].samples holds, per backend, every point’s record: index; status (of the binary64 call: success, best-effort, failed …); value (the binary64 total finite part) and sectors (each squared-order sector’s); the estimate (null without one): estimate_relative (the flag’s metric), estimate_finite_relative (the total’s estimated relative error), estimate_digits, estimate_scale, estimate_checks (each check that ran, by name, e.g. rotation-1, reduction-rescaled, with its own relative budget) and estimate_not_run; flagged (the default checks flag it: estimate above the target, a best-effort value, or none); best_effort and its uncertainty (relative); reason (a refusal or failure); reference_value (the exact decimal text of the reference’s total finite part at its precision; null when it failed or with --ground-truth none), reference_reason and reference_certified (an arbitrary-precision reference’s certification: "agreement" with another backend’s reference, "checks" from its checked evaluation; null for a reference that failed and in every run without an arbitrary-precision ground truth, whose records carry the column all the same: every run’s table has the same fields); true_relative_error and true_digits (null without both values); binary64_task, reference_task (the reference’s first evaluation: plain, or checked with one backend) and reference_checked_task (its checked re-run; null without one), indices into the table’s tasks list of [seconds, points] of the task that evaluated the point (inside a batched call there is no per-sample time); lane_rescue (the point’s lane rescue, e.g. "reduction lanes rescued in double-double"; null without one). Values, sectors, momenta and the reference are exact; the relative errors and scales carry 4 significant digits, the digits 3 decimals, the task seconds microseconds. Non-finite numbers are the texts "inf" / "nan". per_point (the statuses the tables use) is a table of the same form. The aggregate tables are reproducible from these records (the percentiles of true_digits, the flagged and missed counts against stability_setup.target).

--samples-output PATH (benchmark.samples_output) writes the same records to their own file instead, as its own phase: one JSON document with schema "pyamplicol.profile-samples/1", process, seed, sqrt_s, inputs (the setup’s table) and backends (each backend’s table). The report’s samples then name it ({"output": PATH, "points": N}); this also works with the human tables. Without --json or --samples-output no per-sample record is built.

within 10 x its estimate

--precision auto (default) runs binary64 first and double-double only for a row whose binary64 run fails, is refused or is out of its criterion’s scope (a pole row whose relative estimate exceeds the default target accuracy 1e-5 or that carries no estimate; a Ward row with E above 1e-9 of the physical scale or without an estimate); double or double-double runs one carrier alone, and there a row out of its carrier’s scope reads “not run” (exit 3), never a failure or a pass. When binary64 evaluated a point and the double-double run is refused, the rows binary64 left undecided keep its verdict and say that double-double was refused. In auto, a row double-double fails while its residual is within 10 x double-double’s own estimate (asked for only then: the recommended checks for poles, the reduction-direction check for Ward) has run out of digits: only such rows, at their points, are re-run in arbitrary precision at the digit count derived from the shortfall, d = ceil(32.0 + log10(10 E / B)) for an estimate E and a bound B (32.0: double-double’s decimal digits, 1 + log10(0.5 / 2^-104); the largest over the point’s rows; --arbitrary-digits N, check.arbitrary_digits, sets it), the point lifted again at those digits, and judged by their double-double criterion (no new bound; the row shows carrier arbitrary, its digits and the double-double numbers); a double-double residual far above its own estimate stays a failure. A row still undecided there, or undecided at an explicit carrier, reads “undecided” with both carriers’ numbers and counts as a failure (exit 1). The loop-induced probes’ criterion is their own estimate, so they never take this rung. Each double-double and arbitrary-precision rung (and the binary64 one under --kinematics-improvement-binary64) first improves its lifted point per --kinematics-improvement (evaluation. kinematics_improvement, default z-shift) in its own carrier, exactly as evaluate does; check lifts its points onto exact conservation along the beam axis at twice the rung’s digits already, so this moves them by about the rung’s rounding, and each row records it (CheckRow.kinematics: the producing variant, exact or not-improved). The Ward rows of a request whose loop corrections include an electroweak one (any correction other than the model’s strong one) and with an on-shell zero-width external massive quark (a top or a massive b, quark or antiquark) read “not applicable” and are not evaluated: the Ward identity of the asymmetric check is not guaranteed with electroweak corrections there; Ward rows are not split by squared-order sector, so that request’s QCD-loop sectors are not Ward-checked either. A sector Catani’s operators do not predict (a QCD correction of a process with photon-exchange Borns, …) is listed as “no prediction” with its reason; a sector they predict that got no pole row at a point reads “not run” (exit 3: an applicable check did not run); a check that does not apply (no external gluon or photon, no massive vector, a unitary-gauge request) reads “not applicable” with the reason; a Goldstone side the engine refuses reads “not run”. None of these is a pass.

Every row names the check, its subject (sector and pole, leg and factor), the point, the carrier that decided, ratio (the measured value over its bound: <= 1 passes), the deviation and E over the row’s scale where formed (dev / scale, E / scale: a binary64 pole row’s pre-cancellation scale S; a double-double pole row’s |Catani|, its criterion being relative; a Born-interfered Ward row’s physical scale; a probe’s row term floor S_k(h)), the fallback’s reason and the verdict. The exit code is 0 iff every applicable check passed, 1 on any failure, and 3 when a process had nothing to check (or an applicable check did not run); an “undecided” row counts as a failure (1). --json returns the CheckReport (source, source_kind, points, seed, precision, carriers, regeneration, seconds, exit_code, and per process process, expression, contribution, widths, zeroed_widths, reduction, status, seconds and rows with the fields above and digits, the arbitrary-precision carrier’s digit count); carriers ends with arbitrary under auto; source names the run card or artifact checked. Python: pyamplicol.api.check(target, points=..., seed=..., precision=..., model=..., sqrt_s=..., arbitrary_digits=...).

Cost: one probe-slice generation per process (about the generation’s own cost: the request-model preparation included) plus a few evaluations per point; the generation-time probes (generation.loop_induced_probes, off by default) are the same loop-induced checks at one point during generation.

Models¶

Inspect a trusted UFO directory without generating a process:

pyamplicol model inspect models/ufo/sm

Compile portable model IR:

pyamplicol model compile models/ufo/sm models/sm.pyAmplicol-model.json

Prepare a reusable JIT-O2 kernel bundle for eager or recurrence execution:

pyamplicol model compile \
  models/json/sm/sm.json models/ufo-sm-jit-o2.pyamplicol-model \
  --backend jit --jit-optimization-level 2

Enumerate a broad request without writing a process artifact:

pyamplicol model processes "p p > all all" \
  --model built-in-sm --flavor-scheme 1 --max-quark-lines 0

The distinction between portable model IR and prepared kernel bundles is explained in Models and Processes.

The model caches are controlled by --model-cache / --no-model-cache, --model-cache-dir DIR and, for one-loop generation, --loop-preparation-cache / --no-loop-preparation-cache (the persistent cache of the lowered model programs, on by default, [model] loop_preparation_cache; also off with --no-model-cache or PYAMPLICOL_LOOP_PREPARATION_CACHE=0). See Model caches and the one-loop preparation cache.

The common presentation options are:

Values

Meaning

flag

Detect a terminal, force ANSI color, or disable it

By default every command prints its tables and short status lines only: no legends, footnotes or logger-format lines. A few short notice lines (process, model, output, widths, check) say what is being done; they are printed above the progress display, which they never tear. --fields-description-help adds, after the tables, a short heading per table and one line per column (the command runs as usual). What changes the meaning of the numbers stays in the table titles: for example Born-loop interference, leading colour, ..., finite only, ..., UV poles of the bare loop amplitude or ..., IR poles of the renormalised virtual. Every command shows its progress (a live display on a terminal, plain lines with --progress log) and handles Ctrl-C: no traceback, worker processes stopped, exit code 130. After a Ctrl-C:

  • profile prints the tables of what was measured so far, with a one-line notice of how many of the requested points were measured. When the backends measured different numbers of points, the stability tables compare the points that every backend measured.

  • evaluate prints the tables of the points evaluated so far, with the same kind of notice, when it runs with the live progress display on a terminal. There it evaluates its points in successive calls, at a few per cent of extra time. Without a live display, for example with --progress log, --progress off or redirected output, it makes one call, as the Python API does, and a Ctrl-C ends it without a result.

  • In --json mode, a one-loop evaluate records the interruption as the fields interrupted, requested_points and measured_points. A tree-level evaluate keeps its JSON list and prints the notice on stderr. profile sets interrupted, and its stability_setup gives requested, measured_points and evaluated_per_backend.

  • check reports the tests completed and marks the others “not run”, and self-test reports the checks run so far.

  • An interrupted generate writes nothing: an artifact is published only when it is complete.

JSON mode keeps stdout machine-readable; progress and diagnostics use stderr. This makes pipelines predictable:

pyamplicol inspect artifacts/pp_zjj --json > artifact.json

Use --color always only when the consumer understands ANSI escapes. The default auto mode produces colored terminal tables and plain redirected output.

Export recurrence programs¶

Export an LC recurrence artifact without evaluating momenta:

pyamplicol export-recurrence artifacts/gg_ggg -o recurrence.json
pyamplicol export-recurrence artifacts/gg_ggg -o recurrence.json \
  --model-parameters parameters.json --process g_g_to_g_g_g --color-flow flow:1,2,3,4,5

By default the export includes every stored process, alias and process-group member, and every provider colour flow. Repeat --process or --color-flow to select several. Colour-flow IDs are per process and --color-flow applies to every selected process, so combine it with --process on a multi-process artifact; an ID a selected process lacks is refused with that process’s flow IDs. The destination is checked before the export runs, and the file is written beside it and renamed into place, so a failed export leaves an existing file unchanged. --model-parameters reads the same JSON parameter mapping as evaluate and applies it before resolving the programs. The output contains versioned JSON and embedded symjit applications, so external runners do not need a Rust toolchain or the original artifact. The programs describe the batched f64 execution path. See the export format for arithmetic and ordering requirements.

Exports use compact JSON, shared kernel bindings and union bodies, and representative references for aliases and group members. --indent 2 enables readable JSON. Add --reference-points momenta.json to include batched f64 reference values; this is the only export option that evaluates momenta. Kernel applications are embedded as base64.
